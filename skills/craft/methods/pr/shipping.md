### Shipping

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the stack.**

1. **Verify each PR independently before it lands.** GitHub CLI (`gh`) is the forge. A PR's independent verdict is the pipeline's gate acceptance of its milestone: the gate round that accepted the frozen candidate (`/gate`) and the owner's acceptance (`/gate accept`). With the project's workflow OFF there is no gate verdict, so say so and land only what the owner names. Only a verdict from checkers that did not write the code counts, because an author checks what it meant to build. Green CI and an approving bot review are not verdicts, because neither runs the change as a user would.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one whose `land-check` does not pass (step 3). The PRs below it are the run, and the top one is the ceiling. A verified PR above an unverified one waits, because it cannot land without the code below it. One whose branch neither holds nor needs that code can move onto trunk and land on its own. It needs a fresh verdict first, because its old one ran with that code beneath it and trunk does not have it.
3. **Re-check that the verdicts still describe the code.** A verdict covers a product state, and a chain rebase moves every PR above it to a new SHA without failing any check. Run `python3 ~/.claude/skills/_shared/scripts/pr_watch.py land-check` (its `--help` names the arguments) on each PR before it lands. It checks the PR head out in a temporary worktree and passes only when the head's product fingerprint equals the candidate the owner accepted for that milestone, or a focused re-gate accepted the change. Anything else goes through `/fix` and a focused re-gate first, because the old verdict never saw it.
4. **Land bottom-up, one PR at a time.** Always merge the run's lowest unmerged PR, with `gh pr merge <pr> --squash`. On GitHub a PR whose base is still its parent's branch merges into that branch, not trunk. Read the PR back for the result (`gh pr view <pr> --json state,mergedAt,baseRefName`), because a merge command can report success when a merge queue only queued the PR, and a requested auto-merge is not a merge. A landed PR reads merged with trunk as its base, not its parent's branch. Arm `--auto` (GitHub auto-merge) only on a PR whose `land-check` passes at its current head, because it lands whatever head is ready. After a merge lands, retarget the PR whose base was the merged branch to trunk (`gh pr edit <pr> --base <trunk>`), move its patch onto the merge result, and push with `--force-with-lease`. The verdict covers the product state, not its commits, so step 3's `land-check` decides whether the verdict survives. Merge it once its checks pass and its `land-check` passes.
5. **Leave the stack alone while it lands.** Step 4's move of the next PR is the only change to a branch or base, because a merge lands whatever its branch and base hold at that moment, verdict or not. Watch the run with the queued watcher from `babysit.md` (`python3 ~/.claude/skills/_shared/scripts/pr_watch.py --queued-stack --stack-prs <bottom-to-top>`) under Claude Code's `/loop` until it reports `COMPLETE` at the ceiling. A base that moves to trunk when its parent merges is expected, not damage to repair. If a merge stalls, find out why before you change anything.
6. **Stop at the ceiling.** Extending the run takes new verdicts, so it is a new pass through step 1.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, what landed and how you confirmed it, and what the next gap needs.
